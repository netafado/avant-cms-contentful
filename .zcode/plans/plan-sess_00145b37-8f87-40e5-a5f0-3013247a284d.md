## Implement WebMCP in avant-cms-contentful

Add WebMCP support so AI agents browsing the portfolio (Chrome's agent APIs, and future spec-compliant browsers) can discover and call structured tools via `document.modelContext.registerTool()` instead of guessing from the DOM. This complements the existing AI-discoverability stack (llms.txt, AI-bot allowlist in robots.ts, JSON-LD). Types come from the official `webmcp-types` package (devDependency, zero runtime code). In browsers without WebMCP support the bridge feature-detects and no-ops silently.

### 1. Install types
- `npm i -D webmcp-types`
- Create `src/types/webmcp.d.ts` with `/// <reference types="webmcp-types" />` (triple-slash reference rather than tsconfig `types` array, so `@types/jest` etc. auto-inclusion is untouched).

### 2. `src/lib/webmcp/tools.ts` — tool definitions (framework-free, unit-testable)
Five tools, MCP-style `{ name, description, inputSchema, execute }` returning `{ content: [{ type: "text", text }] }`:
- **`get_profile`** — no input. Returns JSON built from existing `src/lib/seo` constants: name, jobTitle, description, skills (knowsAbout), social links (SOCIAL_LINKS), site URL.
- **`list_pages`** — no input. Fetches `${location.origin}/sitemap.xml` (sitemap.ts already exists — no new API route needed), parses with DOMParser, returns `[{ loc, lastmod }]`.
- **`get_page_content`** — no input. Returns current document title, URL, and `document.body.innerText` (whitespace-collapsed, capped ~10k chars).
- **`navigate_to_page`** — input `{ path: string }`. Validates the path is site-relative (rejects external URLs), then `window.location.assign(path)`. Full navigation is intentional — agents get fresh server-rendered content.
- **`toggle_theme`** — no input. Mirrors ThemeProvider behavior: reads localStorage `theme` (default `"dark"`), flips it, persists, toggles the `dark` class on `document.documentElement`. Returns the new theme.

### 3. `src/components/WebMcpBridge/index.tsx` — registration bridge
- `"use client"` component rendering `null`, mounted in `<body>` in `src/app/layout.tsx` so tools exist on every page.
- On mount: feature-detect `"modelContext" in document`; if absent, return early. Otherwise `registerTool()` each definition with a shared `AbortController` signal; abort on unmount. Each registration wrapped in try/catch so one failure can't break the rest.
- With `webmcp-types` installed, `document.modelContext` is properly typed — no `any` casts.

### 4. Tests (Jest + Testing Library, existing jsdom setup)
- `src/lib/webmcp/tools.test.ts` — profile output shape; page-content extraction from a mocked document; navigate validation (external URL rejected, valid path calls assign — jsdom navigation stubbed); theme toggle flips localStorage + class; list_pages with mocked fetch returning sample sitemap XML.
- `src/components/WebMcpBridge/index.test.tsx` — with a mocked `document.modelContext`: all five tools registered and abort fires on unmount; without it: renders null, no crash.

### 5. Docs
- Add a "WebMCP tools" section to `public/llms.txt` and `public/llms-full.txt` listing the five tools, so LLM crawlers and the site's own docs stay in sync.
- Brief note in README.

### 6. Verification
- `npm run lint`, `npm test`, `npm run build`
- `npm run dev` + browser check: no console errors on pages (registration no-ops in unsupported browsers), and with a small `document.modelContext` shim pasted in a dev session, tools register and `toggle_theme` / `get_profile` respond.

Out of scope (deliberately): server-side MCP endpoint (no API routes exist and client-side WebMCP needs none), the declarative HTML form annotation API (portfolio has no forms), and any polyfill dependency.
